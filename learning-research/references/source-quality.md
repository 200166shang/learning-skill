# Source quality

Select for learning value and technical reliability, not search rank or quantity.

## Evidence ladder

1. **Primary and authoritative:** official documentation and tutorials, specifications, standards, official repositories and source code, maintainer design notes. Use these for APIs, architecture, semantics, configuration, and implementation claims.
2. **Strong explanation:** maintainer blogs, respected technical authors, engineering blogs with evidence, conference talks, deep tutorials, and rigorous courses. Use these when they make the mechanism clearer or connect the system better than primary material alone.
3. **Community experience:** issue discussions, Stack Overflow, forums, Reddit, Zhihu, and personal blogs. Use these for common confusion, operational pitfalls, debugging experience, or alternative explanations. Do not use them as the sole authority for an important technical claim when a stronger source exists.

Authority alone is insufficient: recommend a source only when a specific part advances this learner's current understanding. Prefer a few complementary sources over a long list of overlapping links.

## Evaluation

For explanatory articles and videos, check author or publisher credibility, technical depth, specificity, supporting evidence, date relevance, and whether the material explains a mechanism rather than merely listing commands. Exclude shallow summaries, copied material, content farms, and SEO pages that add no verified understanding.

Verify every claimed document section, code path, symbol, behavior, and video chapter in the source itself. Distinguish direct source evidence from inference. Use direct links to the supporting page or repository location.

Remove a source before finishing when it is weak, redundant, mismatched to the learner's level, or lacks a clear role in the reading path.
